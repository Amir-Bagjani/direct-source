# ADR-0003: مونولیت ماژولار Django برای MVP

## وضعیت

Accepted

## تاریخ

2026-09-02

## زمینه و مسئله

بازارگاه در شروع یک تیم و یک محصول دارد، اما دامنهٔ آن شامل هویت، کاتالوگ، سفارش، امور مالی شبیه‌سازی‌شده، ارسال، مغایرت و پشتیبانی است. تراکنش‌ها و قواعد این حوزه‌ها در MVP به‌هم‌پیوسته‌اند و هنوز الگوی بار یا مرزی که استقرار مستقل بخواهد اثبات نشده است.

## محرک‌های تصمیم

- تحویل سریع MVP با پیچیدگی عملیاتی محدود
- تراکنش اتمیک برای سفارش، رزرو، قیمت و کارمزد
- مرز روشن دامنه برای کاهش coupling و امکان رشد آینده
- مشاهده‌پذیری، تست و استقرار ساده برای تیم اولیه

## گزینه‌های بررسی‌شده

### مونولیت ماژولار Django

- مزایا: یک استقرار و دیتابیس تراکنشی، migration و تست ساده‌تر، استفادهٔ مستقیم از admin/ORM/DRF
- معایب: نیاز به انضباط وابستگی؛ scale و release مستقل هر حوزه در ابتدا وجود ندارد

### microservice از ابتدا

- مزایا: استقرار و scale مستقل و ownership سرویس‌ها
- معایب: تراکنش توزیع‌شده، سازگاری eventual، قرارداد شبکه، observability و عملیات بسیار بیشتر بدون نیاز اثبات‌شده

### مونولیت بدون مرز ماژول

- مزایا: شروع سریع‌تر در روزهای اول
- معایب: coupling مدل‌ها و منطق، migration و تست دشوار و هزینهٔ جداسازی بالا

## تصمیم

بک‌اند MVP یک deployment از Django خواهد بود، ولی قابلیت‌ها در Django appهای دامنه‌ای با ownership داده و جهت وابستگی مشخص جدا می‌شوند. ارتباط متقابل از service/command و event داخلی مشخص عبور می‌کند.

## دلیل

این گزینه سادگی عملیاتی و تراکنش قوی موردنیاز MVP را حفظ می‌کند، بدون آنکه مرز دامنه قربانی سرعت شروع شود. اگر بعداً load، ownership تیم یا نیاز استقرار مستقل اثبات شود، یک ماژول دارای مرز روشن گزینهٔ مناسب‌تری برای استخراج است.

## پیامدها

### مثبت

- یک CI/CD، یک migration graph و یک observability surface
- transactionهای محلی برای گردش‌های مالی و سفارش
- امکان استفاده از امکانات بومی Django

### منفی و ریسک‌ها

- importهای دوری و دسترسی مستقیم بین appها می‌توانند مرزها را از بین ببرند.
- یک خرابی یا release می‌تواند کل backend را تحت‌تأثیر قرار دهد.
- دیتابیس و deployment مستقل هر دامنه فعلاً ممکن نیست.

### اقدامات لازم

- dependency rule و architecture test برای importهای دامنه تعریف شود.
- model ownership و public service API هر app مستند شود.
- رخدادهای داخلی و تراکنش‌ها طوری طراحی شوند که retry idempotent باشد.
