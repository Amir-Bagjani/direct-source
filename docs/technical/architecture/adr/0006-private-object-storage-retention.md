# ADR-0006: ذخیره‌سازی خصوصی و نگهداری پیش‌فرض دائمی فایل‌های حساس

## وضعیت

Accepted

## تاریخ

2026-09-03

## زمینه و مسئله

فرایند تأیید کسب‌وکار، مغایرت و پشتیبانی شامل کارت ملی، تصویر چهره، مجوز، شواهد فعالیت و مدارک تصویری اختلاف است. این فایل‌ها برای بررسی، سابقهٔ تصمیم و رسیدگی‌های بعدی لازم‌اند، اما افشای آن‌ها آسیب‌زا است. مالک محصول تصمیم گرفته فایل‌ها به‌صورت خودکار منقضی یا حذف نشوند، در حالی که مسیر حذف معتبر یا قانونی باید باقی بماند.

## محرک‌های تصمیم

- فایل حساس نباید URL عمومی یا دسترسی پیش‌فرض داشته باشد.
- مدارک و تصمیم مرتبط باید در بررسی‌های بعدی قابل‌ردیابی بمانند.
- حذف زمان‌بندی‌شده یا lifecycle خودکار برای فایل‌های حساس مطلوب نیست.
- درخواست معتبر حذف، دستور قانونی و منع نگهداری باید قابل‌اجرا باشند.
- مشاهده، دانلود و حذف باید قابل‌حسابرسی باشند.
- انتخاب ارائه‌دهندهٔ نهایی storage نباید مدل دامنه را تغییر دهد.

## گزینه‌های بررسی‌شده

### گزینهٔ ۱: نگهداری فایل در فایل‌سیستم سرور

- مزایا: راه‌اندازی سادهٔ محلی
- معایب: مقیاس‌پذیری، backup، دسترس‌پذیری و کنترل دسترسی ضعیف‌تر؛ وابستگی به ماشین اجرا

### گزینهٔ ۲: object storage خصوصی با حذف خودکار زمان‌بندی‌شده

- مزایا: کاهش حجم و سطح مواجههٔ داده پس از مدت مشخص
- معایب: احتمال حذف مدرک موردنیاز و ناسازگاری با تصمیم نگهداری پیش‌فرض دائمی

### گزینهٔ ۳: object storage خصوصی، بدون حذف خودکار و با حذف دستی کنترل‌شده

- مزایا: حفظ سابقه، کنترل دسترسی مناسب، استقلال از provider و امکان اجرای استثناهای معتبر حذف
- معایب: رشد دائمی هزینه و سطح دادهٔ حساس، نیاز به کنترل امنیتی و فرایند حذف دقیق

## تصمیم

گزینهٔ ۳ انتخاب شد:

- اصل فایل و مشتقات آن در object storage خصوصی و S3-compatible نگهداری می‌شوند؛ PostgreSQL فقط metadata، مالکیت، purpose، hash، وضعیت و کلید object را نگه می‌دارد.
- bucket یا container عمومی ممنوع است. دریافت فایل فقط از مسیر مجوز Django و URL امضاشدهٔ کوتاه‌عمر انجام می‌شود.
- فایل‌ها در انتقال و در حالت سکون رمزگذاری می‌شوند و secretهای storage خارج از repository می‌مانند.
- دسترسی فقط برای بارگذار/مالک پرونده و اپراتور دارای مجوز و نیاز کاری مجاز است؛ مشاهده و دانلود فایل حساس در audit trail ثبت می‌شود.
- فایل‌های حساس به‌صورت پیش‌فرض برای مدت نامحدود نگهداری می‌شوند و lifecycle یا job حذف خودکار ندارند.
- حذف فقط با عملیات دستی دامنه‌ای، درخواست معتبر صاحب داده یا دستور قانونی، تأیید مالک سامانه و ثبت دلیل انجام می‌شود.
- وجود پروندهٔ باز، اختلاف فعال یا منع قانونی، حذف را تا رفع مانع متوقف می‌کند.
- حذف تأییدشده باید اصل، thumbnail/preview، نسخه‌های قابل‌دسترسی و cache را پوشش دهد. یک tombstone غیرحساس شامل شناسه، زمان، عامل و دلیل حذف در audit باقی می‌ماند.
- فرایند restore از backup باید tombstoneهای حذف را دوباره اعمال کند تا فایل حذف‌شده ناخواسته بازنگردد.
- متن رضایت و purpose جمع‌آوری پیش از upload نمایش و نسخهٔ پذیرفته‌شده ثبت می‌شود.

## دلیل

object storage خصوصی کنترل دسترسی و رشد مستقل فایل را فراهم می‌کند. نگهداری پیش‌فرض دائمی خواستهٔ مالک محصول را اجرا می‌کند، اما مسیر حذف دستی اجازه می‌دهد درخواست معتبر، دستور قانونی یا تصمیم بعدی بدون دستکاری مستقیم storage انجام شود.

## پیامدها

### مثبت

- فایل حساس از web root و دیتابیس تراکنشی جدا می‌ماند.
- تغییر provider یا اتصال storage واقعی، مدل پرونده‌ها را بازنویسی نمی‌کند.
- تمام دسترسی‌ها و حذف‌ها قابل‌ردیابی‌اند.
- حذف تصادفی ناشی از lifecycle خودکار رخ نمی‌دهد.

### منفی و ریسک‌ها

- هزینه و حجم storage به‌طور پیوسته رشد می‌کند.
- نگهداری طولانی، اثر بالقوهٔ رخداد امنیتی را افزایش می‌دهد.
- درخواست حذف نیازمند فرایند عملیاتی و بررسی دستی است.
- مدت نگهداری نامحدود و متن رضایت باید پیش از پایلوت واقعی توسط مشاور حقوقی بازبینی شوند.

### اقدامات لازم

- مدل `StoredFile` یا معادل آن، purpose، classification، owner، hash، status و deletion hold داشته باشد.
- policy مجوز مشاهده، دانلود و حذف برای هر نوع فایل آزموده شود.
- نوع، حجم، signature واقعی فایل و بدافزار پیش از قابل‌دسترسی‌شدن بررسی شوند.
- URL امضاشده کوتاه‌عمر و غیرقابل‌فهرست‌شدن باشد.
- runbook حذف دستی، legal hold، backup restore و رخداد افشای فایل نوشته شود.
- هزینه و رشد storage در داشبورد عملیات پایش شود.
