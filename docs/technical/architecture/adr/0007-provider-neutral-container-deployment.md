# ADR-0007: استقرار کانتینری مستقل از ارائه‌دهنده

## وضعیت

Accepted

## تاریخ

2026-09-03

## زمینه و مسئله

MVP از Next.js، Django، worker/scheduler، PostgreSQL، Redis و object storage تشکیل می‌شود. شرکت میزبان، بودجهٔ قطعی و سرویس‌های مدیریت‌شدهٔ قابل‌دسترسی هنوز انتخاب نشده‌اند. بااین‌حال topology و مرزهای شبکه باید پیش از ساخت CI/CD روشن باشند تا انتخاب بعدی ارائه‌دهنده باعث بازطراحی برنامه نشود.

## محرک‌های تصمیم

- امکان جابه‌جایی میان ارائه‌دهندگان بدون تغییر منطق دامنه
- جداسازی سرویس‌های عمومی از Django و داده‌های خصوصی
- یکسان‌بودن نسبی محیط local، staging و production
- امکان انتخاب provider براساس پایداری، دسترسی از ایران و هزینه در زمان نزدیک به استقرار
- backup و restore مستقل از خرابی یک میزبان
- پرهیز از Kubernetes و زیرساخت پیچیدهٔ زودهنگام برای MVP

## گزینه‌های بررسی‌شده

### گزینهٔ ۱: انتخاب فوری یک PaaS و استفاده از قابلیت‌های اختصاصی آن

- مزایا: شروع سریع deployment و عملیات کمتر
- معایب: تصمیم زودهنگام بدون بودجه و سنجش دسترسی، وابستگی به vendor و احتمال بازطراحی

### گزینهٔ ۲: نصب همهٔ اجزا روی یک سرور عمومی

- مزایا: هزینه و پیچیدگی اولیهٔ کم
- معایب: سطح حمله و blast radius بزرگ، جدانبودن داده از ورودی عمومی و مسیر recovery ضعیف‌تر

### گزینهٔ ۳: کانتینرهای provider-neutral با مرز شبکهٔ عمومی/خصوصی

- مزایا: قابلیت انتقال، topology روشن، جداسازی امنیتی و امکان استفاده از سرویس مدیریت‌شده در هر provider
- معایب: نیازمند نگهداری image، secrets، networking، backup و monitoring استاندارد

## تصمیم

گزینهٔ ۳ انتخاب شد:

- Next.js، Django web، Celery worker و scheduler به‌صورت imageهای کانتینری قابل‌تکرار ساخته می‌شوند.
- Next.js/BFF ورودی عمومی برنامه است و TLS در edge یا reverse proxy خاتمه می‌یابد.
- Django، PostgreSQL و Redis در شبکهٔ خصوصی قرار می‌گیرند و مستقیماً از اینترنت عمومی قابل‌دسترسی نیستند.
- object storage از API سازگار با S3 و policy خصوصی ADR-0006 استفاده می‌کند.
- staging و production حساب، شبکه، secrets، دیتابیس، bucket و دادهٔ جدا دارند.
- configuration از environment/secret manager تزریق می‌شود و هیچ منطق دامنه‌ای به API اختصاصی provider وابسته نمی‌شود.
- PostgreSQL مدیریت‌شده ترجیح دارد؛ اگر انتخاب نهایی self-hosted باشد، backup، monitoring، patching و restore drill الزامی‌اند.
- backupها رمزگذاری‌شده و در failure domain جدا نگهداری می‌شوند و restore پیش از پایلوت تمرین می‌شود.
- ارائه‌دهندهٔ نهایی حداکثر پیش از ساخت staging براساس دسترسی پایدار از ایران، هزینه، region/data constraints، سرویس‌های مدیریت‌شده، backup و observability انتخاب می‌شود.
- این تصمیم استفاده از Docker را الزام می‌کند، اما orchestrator production را از پیش به Kubernetes یا محصول مشخصی محدود نمی‌کند.

## دلیل

این topology مرز امنیتی و بسته‌بندی اجرا را اکنون تثبیت می‌کند، اما تصمیم وابسته به قیمت و دسترسی شرکت‌های میزبان را تا زمانی که اطلاعات واقعی موجود باشد عقب می‌اندازد. بنابراین development می‌تواند بدون فرض vendor شروع شود.

## پیامدها

### مثبت

- محیط‌ها با artifact یکسان deploy می‌شوند.
- تغییر provider عمدتاً به زیرساخت و CI/CD محدود می‌ماند.
- دیتابیس و Redis در معرض مستقیم اینترنت نیستند.
- انتخاب سرویس مدیریت‌شده یا self-hosted بعداً ممکن است.

### منفی و ریسک‌ها

- تفاوت شبکه، object storage و secret manager ارائه‌دهندگان همچنان به adapter و runbook نیاز دارد.
- تأخیر بیش از حد در انتخاب provider می‌تواند staging و تست recovery را عقب بیندازد.
- تحریم، اختلال دسترسی یا محدودیت انتقال داده می‌تواند گزینه‌های میزبانی را تغییر دهد.
- self-hosting PostgreSQL هزینهٔ عملیاتی و ریسک بیشتری از سرویس مدیریت‌شده دارد.

### اقدامات لازم

- Dockerfileهای production-grade و health check برای Next.js، Django، worker و scheduler ساخته شوند.
- network policy یا firewall فقط مسیرهای لازم را باز کند.
- migration به‌صورت job کنترل‌شده و تک‌اجرا باشد.
- secrets، backup، restore، rollback، monitoring و incident runbook پیش از staging تعریف شوند.
- ماتریس ارزیابی provider پیش از staging با معیارهای هزینه، دسترسی، SLA، PostgreSQL، S3، backup و خروج داده تکمیل شود.
