# ADR-0008: API نسخه‌دار REST با DRF و OpenAPI

## وضعیت

Accepted

## تاریخ

2026-09-03

## زمینه و مسئله

Next.js مصرف‌کنندهٔ اصلی بک‌اند است و برای توسعهٔ مستقل frontend و backend به قراردادی روشن، قابل‌آزمون و قابل‌نسخه‌بندی نیاز دارد. API باید با معماری مونولیت ماژولار Django سازگار باشد و بدون افزودن پیچیدگی غیرضروری، عملیات دامنه، خطاها و تغییرات ناسازگار آینده را مدیریت کند.

## محرک‌های تصمیم

- سازگاری بومی با Django و سیاست‌های احراز هویت و مجوز
- قرارداد قابل‌خواندن برای frontend و قابل‌بررسی در CI
- نسخه‌بندی صریح تغییرات ناسازگار
- ابزارها و الگوهای بالغ برای validation، serialization و pagination
- سادگی مناسب MVP و امکان توسعهٔ تدریجی

## گزینه‌های بررسی‌شده

### Django REST Framework و REST JSON

- مزایا: یکپارچگی قوی با Django، ابزار بالغ برای serializer، permission و testing، پشتیبانی مناسب از OpenAPI
- معایب: endpointها و schema باید منظم نگهداری شوند و ممکن است برخی پاسخ‌ها برای نیاز دقیق صفحه دادهٔ اضافه داشته باشند

### GraphQL

- مزایا: انتخاب فیلد توسط مصرف‌کننده و قرارداد schemaمحور
- معایب: پیچیدگی بیشتر در authorization، caching، محدودکردن query و عملیات تیم برای نیاز فعلی MVP

### endpointهای سفارشی بدون framework قرارداد

- مزایا: وابستگی کمتر و آزادی کامل در پیاده‌سازی
- معایب: تکرار validation، خطا، مستندسازی و تست قرارداد و افزایش احتمال ناسازگاری frontend/backend

## تصمیم

API عمومی بک‌اند با Django REST Framework و REST JSON ساخته می‌شود. همهٔ endpointهای نسخهٔ نخست زیر `/api/v1/` قرار می‌گیرند و قرارداد آن‌ها با OpenAPI 3 تولید، منتشر و در CI اعتبارسنجی می‌شود. تغییر ناسازگار قرارداد عمومی نیازمند نسخهٔ major جدید است؛ تغییر سازگار در همان نسخه انجام می‌شود.

ارتباط داخلی appهای Django از HTTP عبور نمی‌کند و طبق ADR-0003 از service/command و event داخلی مشخص استفاده می‌کند.

## دلیل

DRF کوتاه‌ترین مسیر برای ارائهٔ API امن و قابل‌آزمون روی Django است. نسخه‌بندی URL قرارداد مصرف‌کننده را شفاف می‌کند و OpenAPI امکان هماهنگی و کشف اختلاف میان backend و Next.js را پیش از استقرار فراهم می‌سازد.

## پیامدها

### مثبت

- قرارداد واحد و قابل‌تولید برای frontend، تست و مستندات وجود دارد.
- رفتار validation، permission، pagination و خطا می‌تواند در تمام endpointها یکسان شود.
- تغییرات ناسازگار به‌صورت صریح از نسخهٔ قبلی جدا می‌شوند.

### منفی و ریسک‌ها

- schema تولیدشده ممکن است از رفتار واقعی endpoint فاصله بگیرد.
- نگهداری هم‌زمان چند نسخهٔ API در آینده هزینه ایجاد می‌کند.
- serializerهای متصل مستقیم به model می‌توانند مرز دامنه را تضعیف کنند.

### اقدامات لازم

- contract test و validation فایل OpenAPI در CI اجرا شود.
- قالب خطای مشترک، pagination و قواعد نام‌گذاری پیش از اولین endpoint تثبیت شوند.
- serializer و view نباید منطق دامنه یا transition وضعیت را مستقیماً اجرا کنند؛ این کار از service/command انجام شود.
- نسخهٔ دقیق DRF و ابزار OpenAPI هنگام scaffold در lockfile قفل شوند.
