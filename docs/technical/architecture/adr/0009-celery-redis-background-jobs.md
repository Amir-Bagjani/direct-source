# ADR-0009: کارهای پس‌زمینه با Celery و Redis

## وضعیت

Accepted

## تاریخ

2026-09-03

## زمینه و مسئله

بازارگاه کارهایی دارد که نباید زمان پاسخ API را طولانی کنند یا به بازبودن درخواست کاربر وابسته باشند؛ از جمله انقضای مهلت‌ها، آزادکردن رزرو، ساخت اعلان، پردازش فایل و retry یکپارچه‌سازی‌های آینده. اجرای این کارها باید قابل‌تکرار، قابل‌مشاهده و مستقل از وضعیت موقت صف باشد.

## محرک‌های تصمیم

- اجرای غیرهم‌زمان و زمان‌بندی‌شده خارج از request وب
- retry کنترل‌شده و مشاهده‌پذیری failureها
- سازگاری بومی با Django و استقرار کانتینری
- جلوگیری از تبدیل صف یا cache به منبع حقیقت دامنه
- سادگی عملیاتی مناسب MVP

## گزینه‌های بررسی‌شده

### Celery با Redis

- مزایا: اکوسیستم بالغ Django، worker و scheduler مستقل، retry و routing و monitoring شناخته‌شده
- معایب: سرویس عملیاتی اضافه و نیاز به طراحی idempotency و مدیریت پیام تکراری

### cron یا management command مبتنی بر دیتابیس

- مزایا: اجزای کمتر و اتکای مستقیم به PostgreSQL
- معایب: امکانات محدودتر برای صف، retry، concurrency، routing و مشاهده‌پذیری کارهای متنوع

### اجرای هم‌زمان در request

- مزایا: ساده‌ترین مدل پیاده‌سازی اولیه
- معایب: افزایش latency، وابستگی کار به اتصال کاربر و ناتوانی در اجرای مطمئن مهلت‌ها و retry

## تصمیم

کارهای پس‌زمینه و زمان‌دار با Celery اجرا می‌شوند. Redis broker صف و cache غیرقطعی است و scheduler دوره‌ای کارهای موعددار را راه‌اندازی می‌کند. PostgreSQL تنها منبع حقیقت وضعیت دامنه، deadline، نتیجهٔ کار و سابقهٔ لازم است؛ از دست‌رفتن Redis نباید حقیقت سفارش یا گردش را از بین ببرد.

taskها حداقل با تضمین اجرای at-least-once طراحی می‌شوند و بنابراین باید idempotent باشند. پیام صف به‌جای حمل state دامنه، شناسهٔ رکورد را حمل می‌کند و worker وضعیت معتبر را دوباره از PostgreSQL می‌خواند.

## دلیل

Celery و Redis نیازهای فعلی صف و زمان‌بندی را با کمترین اصطکاک در پشتهٔ Django پوشش می‌دهند. نگه‌داشتن state قطعی در PostgreSQL، ریسک پیام گمشده، تکراری یا قدیمی را محدود و بازیابی سرویس صف را ممکن می‌کند.

## پیامدها

### مثبت

- API منتظر عملیات کند یا قابل‌retry نمی‌ماند.
- worker و scheduler مستقل از web قابل‌اجرا و scale هستند.
- از دست‌رفتن cache یا بازسازی صف به از دست‌رفتن state دامنه منجر نمی‌شود.

### منفی و ریسک‌ها

- پیام ممکن است بیش از یک بار تحویل شود یا پس از تغییر وضعیت رکورد اجرا شود.
- Redis، worker و scheduler به monitoring و runbook جدا نیاز دارند.
- dispatch پیام هم‌زمان با commit دیتابیس می‌تواند دچار شکاف تراکنشی شود.

### اقدامات لازم

- هر task کلید idempotency، retry محدود، timeout و ثبت نتیجه/خطای قابل‌ردیابی داشته باشد.
- worker پس از lock یا بررسی optimistic، state و deadline جاری را از PostgreSQL اعتبارسنجی کند.
- برای dispatch پس از commit از transactional outbox یا الگوی تضمین‌شدهٔ هم‌ارز استفاده شود.
- health check، عمق صف، سن پیام، نرخ retry/failure و فعال‌بودن scheduler پایش شوند.
- نسخه‌های دقیق Celery و Redis هنگام scaffold قفل و سازگاری آن‌ها آزموده شود.
