# سوابق تصمیم معماری (ADR)
ADR چرایی تصمیم‌های مهم و پرهزینهٔ فنی را نگه می‌دارد. task و وضعیت اجرا در برنامهٔ توسعه پیگیری می‌شوند، نه در ADR.

| --- | --- | --- |
| 0001 | بازارگاه مدیریت‌شده، نه فروشندهٔ مجدد | Accepted |
| 0002 | جداسازی سه محور دسترسی | Accepted |
| 0003 | مونولیت ماژولار Django برای MVP | Accepted |
| 0004 | PostgreSQL به‌عنوان دیتابیس اصلی | Accepted |
| 0005 | احراز هویت JWT با مرجعیت Django و لایهٔ NextAuth | Accepted |
| 0006 | ذخیره‌سازی خصوصی و نگهداری پیش‌فرض دائمی فایل‌های حساس | Accepted |
| 0007 | استقرار کانتینری مستقل از ارائه‌دهنده | Accepted |
| 0008 | API نسخه‌دار REST با DRF و OpenAPI | Accepted |
| 0009 | کارهای پس‌زمینه با Celery و Redis | Accepted |

## فرایند
- فایل `template.md` با شمارهٔ بعدی کپی شود.

- context، driverها، گزینه‌ها، trade-off و پیامدهای منفی نیز نوشته شوند.

- ADR در pull request بازبینی شود.

- پس از توافق، وضعیت از `Proposed` به `Accepted` تغییر کند.

- تصمیم پذیرفته‌شده بازنویسی معنایی نمی‌شود؛ ADR تازه آن را `Superseded` می‌کند.
