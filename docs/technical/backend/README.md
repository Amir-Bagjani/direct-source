# مرکز برنامه‌ریزی توسعهٔ بک‌اند

این پوشه نقطهٔ شروع طراحی و اجرای بک‌اند بازارگاه است. هدف آن تبدیل اسناد محصول به تصمیم‌های فنی، مدل داده، قرارداد API و تسک‌های کوچک و قابل‌سنجش است؛ هنوز در این مرحله کدی تولید نمی‌شود.

## وضعیت

- مرحلهٔ فعلی: نقشهٔ تصمیم‌گیری بسته و پروژه آمادهٔ نوشتن PRD-01 تا PRD-08 است
- معماری پذیرفته‌شده: مونولیت ماژولار Django طبق ADR-0003
- دیتابیس پذیرفته‌شده: PostgreSQL طبق ADR-0004
- runtime پذیرفته‌شده: آخرین patch از Python 3.13 و Django 5.2 LTS؛ patch دقیق هنگام scaffold قفل می‌شود
- API پذیرفته‌شده: REST JSON با Django REST Framework، مسیر `/api/v1/` و قرارداد OpenAPI 3 طبق ADR-0008
- کار پس‌زمینهٔ پذیرفته‌شده: Celery با Redis برای broker/cache و PostgreSQL به‌عنوان منبع حقیقت طبق ADR-0009
- عملیات داخلی پذیرفته‌شده: پنل سفارشی برای اپراتورها و Django Admin محدود برای مالک/کاربر فنی طبق ADR-0010
- طرح معماری: `Accepted`؛ برنامهٔ مرحله‌ای تا نوشته و پذیرفته‌شدن ۸ PRD در حال بازبینی است
- مانع شروع کدنویسی: PRD-01 تا PRD-08 هنوز نوشته و پذیرفته نشده‌اند
- خروجی بعدی: نوشتن PRDها به‌ترتیب وابستگی؛ سپس مدل دامنه، چرخه‌های وضعیت و ERD

## روش مورد استفاده

این برنامه از پنج زاویه ساخته و نگهداری می‌شود:

1. **معماری دیتابیس**: ابتدا دامنه، الگوهای دسترسی، قیود، تراکنش‌ها و مدل داده تعیین می‌شوند.
2. **معماری بک‌اند**: مرز ماژول‌ها، قراردادهای API، امنیت، مشاهده‌پذیری و استقرار مشخص می‌شوند.
3. **الگوهای Django**: ساختار پروژه، Django appها، ORM، DRF، تست و کارهای پس‌زمینه به‌شکل بومی Django طراحی می‌شوند.
4. **شکستن کار**: هر فاز به تسک‌های کوچک با وابستگی، معیار پذیرش و روش راستی‌آزمایی تبدیل می‌شود.
5. **مستندسازی تصمیم‌ها**: تصمیم‌های پرهزینه یا سخت‌برگشت به‌صورت ADR ثبت می‌شوند؛ ADR پذیرفته‌شده ویرایش معنایی نمی‌شود و تغییر آن ADR جدید می‌خواهد.

برای شکاف‌های محصول موجود، اسکیل `grilling` تصمیم‌ها را یک‌به‌یک با پیشنهاد مشخص از کاربر می‌گیرد، `domain-modeling` واژه‌های حل‌شده را همان لحظه در واژه‌نامه تثبیت می‌کند و `to-spec` پس از پایان مصاحبه، تصمیم‌های بسته‌شده را به PRD تبدیل می‌کند. پس از آن `database-architect`، `backend-architect`، `django-pro`، `planning-and-task-breakdown` و `documentation-and-adrs` مسیر فنی را ادامه می‌دهند.

## چرخهٔ نگهداری

- پیش از شروع هر فاز، سؤال‌های باز همان فاز بسته و ADRهای لازم پذیرفته شوند.
- هر تسک باید به حداقل یک نیازمندی و یک معیار پذیرش قابل‌آزمون متصل باشد.
- هر تغییر در مدل داده، چرخهٔ وضعیت یا قرارداد عمومی API باید هم‌زمان در سند فنی مربوط ثبت شود.
- وضعیت تسک‌ها فقط در `implementation-plan.md` تغییر می‌کند؛ ADR محل پیگیری کار نیست.
- پس از هر checkpoint، اسناد، migrationها، OpenAPI و تست‌ها با یکدیگر تطبیق داده شوند.
