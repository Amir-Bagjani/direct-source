# نگهداری و حذف دستی فایل

اصل فایل خصوصی است و انقضای خودکار ندارد. classification از purpose مشتق می‌شود: مدارک identity/activity از نوع restricted و سایر purposeها private هستند. اعتبار URL امضاشده حداکثر ۶۰ ثانیه است. دریافت مجاز در AuditEvent ثبت می‌شود؛ خود URL در audit ذخیره نمی‌شود.

مالک سامانه پس از احراز درخواست معتبر صاحب داده یا دستور معتبر، با `POST /api/v1/operations/files/{id}/hold/` و بدنهٔ `enabled` و `reason` منع حذف را ثبت یا رفع می‌کند. `POST /api/v1/operations/files/{id}/delete/` با `reason` فرمان تأیید و حذف است. نقش اپراتور یا مالک کسب‌وکار به‌تنهایی اجازهٔ حذف ندارد.

فایل با legal_hold و فایل کسب‌وکاری که بررسی اعتماد/محصول، سفارش نهایی‌نشده، تیکت باز یا بررسی/تعلیق باز دارد حذف نمی‌شود. این کنترل عمداً محافظه‌کارانه در سطح کسب‌وکار است. برای پروندهٔ بسته همچنان تأیید و دلیل مالک سامانه لازم است.

فرمان ابتدا deleted_at و رویداد file.deletion_approved را در PostgreSQL commit می‌کند. از این زمان API دیگر URL جدید صادر نمی‌کند. سپس خارج از تراکنش دیتابیس اصل فایل حذف می‌شود؛ در مخزن S3 نسخه‌دار تمام Versionها و DeleteMarkerهای دقیقاً همان کلید حذف می‌شوند. objectهای دیگر با پیشوند مشابه دست‌نخورده می‌مانند. این نسخهٔ بک‌اند thumbnail/preview ذخیره‌شده یا cache عمومی فایل ندارد؛ اگر در آینده اضافه شوند، حذف آن‌ها باید به adapter افزوده شود.

شکست مخزن پاسخ 503 و tombstone حفظ‌شده دارد؛ همان POST برای تکمیل حذف تکرار می‌شود. موفقیت، purged_at و file.purged را ثبت می‌کند. تکرار پس از موفقیت اثر جدیدی ندارد. metadata و روابط تاریخی حذف نمی‌شوند. URL صادرشدهٔ قبلی تا انقضای ۶۰ثانیه‌ای یا حذف object ممکن است معتبر بماند؛ برای رخداد افشا دسترسی مخزن نیز باید بسته شود.

پس از restore از backup، قبل از بازکردن ترافیک و مخزن، tombstoneهای جدیدتر را از نسخهٔ مستقل audit/DB بازیابی کنید؛ backup قدیمی به‌تنهایی تاریخچهٔ حذف بعد از خودش را ندارد. سپس فرمان زیر را با UUID مالک سامانهٔ فعال اجرا کنید:

```sh
python manage.py reapply_file_tombstones --actor OWNER_UUID --reason 'اعمال حذف‌های تأییدشده پس از restore'
```

این فرمان فقط فایل‌های دارای deleted_at را دوباره از مخزن حذف و file.tombstone_reapplied را ثبت می‌کند؛ هیچ فایلِ بدون تأیید حذف هدف قرار نمی‌گیرد. شکست، فرمان را متوقف می‌کند و ترافیک تا موفقیت retry بسته می‌ماند. backup/restore واقعی و پوشش کپی‌های provider باید در staging تمرین و تأیید شوند؛ تست فعلی از adapter شبیه‌سازی‌شده استفاده می‌کند.
